## 第 1 层 · 记录

`01_raw_trk/*.trk` 是 MRC 眼动仪的文本日志：每个样本一行，任务程序打点的地方多一行 `SoftwareEvent`。这一层不是我们产生的，也从不修改。

## 第 2 层 · 样本

`trk2csv.m` 把一份日志变成一个 CSV：一样本一行，带 `pupil_valid` 和落在该样本上的事件。异常（缺 `START`、时间不单调、gap、cue 时长不对）**只记录**——单文件写 `<name>_issues.csv`，整文件夹写 `02_all_issues.csv`——不修补。

要点：眼动仪自己的列（`pupil_2a/2b`、`gaze_x/y`）原样保留；`participant`、`run`、`trial`、`phase` 是推出来的，其中 `run` 只数 `START`——所以缺第一个 `START` 的文件第一段会被标成 run 0。

## 第 3 层 · marker

第 2 层分出两条支线，另有一条直接来自第 1 层，彼此都不依赖：

- **去瞳孔指标**：`csv2kretmat.m` 把逐样本 CSV 改写成 Kret 格式（`.mat`、时间从 0 起、单眼、像素），并按 trial 定义四个段。
- **去事件时间线**：`exportEvents.m` 直接从 trk 写出 `03_events/<sub>_events.csv`，一行一个 `SoftwareEvent`，带事件自己的时刻。
- **去事件表**：`ymtcEventTable.m` 读这条时间线加任务的 `TrialOrder` 工作簿，判断被试跑的是哪套序列，然后按 `Onset → 倒计时 → Outcome → WhiteNoise → Rating` 一行一个 marker 写出去。

为什么是两张表而不是一张：逐样本 CSV 里也有 `event` 列，但事件是挂在“时间戳 ≥ 事件时刻”的第一个样本上，最多晚一个采样间隔（约 17 ms）。用它判断“这个样本属于哪个阶段”没问题，用来算 `diff_s` 就错了——所以事件时间线单独导出，时刻是精确的。

## 第 4 层 · 数字

`example_kret_pipeline.m` 跑 pupil-size 的模型：三道伪影滤波 → 插值到 1000 Hz → 4 Hz 零相位低通 → 按段统计。细节见 [03](03_瞳孔算法.md)，每一列见 [02](02_列字典.md)。

随后 `ymtcTrialQC.m` 套用分析方案的三条规则，写出 `04_all_trials_qc.csv` / `04_all_subjects_qc.csv`。

## 第 5 层 · 一张表

`ymtcMergeResults.m` 把同一个 trial 的事件行和四个段的统计拼成一行：18 + 48 + 3 = 69 列。分析真正从这里开始。

## 三个便宜但救命的检查

| 检查 | 守住什么 | 输出 |
|---|---|---|
| `ymtcRunCheck` | `run = ceil(trial/21)` 这个前提 | `07_checks/07_all_run_check.csv` |
| `ymtcTimingCheck` | 任务是不是按计划跑的 | `05_markers/05_all_timing_check.csv` |
| `checkDocs` | 列字典是否还和表对得上 | 终端 |

## 有意不做的事

- **不做基线校正**。`baseline` 段留着，减不减是分析阶段的事。
- **不在管线里删 trial**。`RejectCountdown` 只标记，删不删写在分析方案里。
- **不做统计检验**。这一层的产出是表，不是结论。
